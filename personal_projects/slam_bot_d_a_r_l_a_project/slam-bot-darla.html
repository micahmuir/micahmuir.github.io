SLAM Bot (D.A.R.L.A)

Daringly Asinine Research in Locomotion and Autonomy,

or,

Delusional Anthropomorphizing Really Lowers Apprehension.

I wanted a robot to test out sensor interactions and use in my future Touchdesigner Installations, so I built one. I wanted something that was unmistakably a robot, but could still generate an emotional response in a human. I wanted someone who isn’t deeply connected to machines to pick up the controller or view a faceless Darla in autonomous mode, and say “hey that’s cute!”

The wheeled platform started as a hacked hoverboard motor set with ODrive controllers, but I quickly found the 90 cpr resolution of my hoverboard motors was woefully inaccurate for the sort of slow, controlled, high torque movement I was aiming for. Sure, they were crazy powerful and really fast, but I wanted a platform that would be safe and comfortable to operate indoors. Ultimately, after a failed attempt to install my own absolute encoder inside the hub robot with no lathe or drill press, I caved and procured 4x M0601 hub motors with built-in 4096 cpr encoders and RS485 drivers. While less powerful than my original two wheels + caster design, the four working together were more than enough to drive my platform, at the cost of skid steering. Someday I’d love to install an Ackerman, or even swerve drive, but for now skid steering is acceptable as long as I have lidar and inertial input as part of the fusion.

The onboard Pi serves a console page as a control interface, but one can also use an Xbox controller for RC mode.

The system highlights:

  • Raspberry Pi 5 main computer
  • Front and backend primarily developed using Claude Code
  • ESP32-S3 with W5500 Ethernet adaptor
  • Dual C1 Slamtec lidars for close range, with an optional VLP16 for enhanced long range measurement
  • Arducam ToF for detailed near-field object detection, potential gesture recognition input
  • 9 DoF IMU unit
  • Bluetooth connection to a speaker for TTS actions
  • ADB interface with the onboard projector for TouchDesigner integration
  • Onboard led matrix and spectrometer for color/projection based triggers
  • LiFePO4 battery - LiPos would work better, but with my available tools and desire to have this little robot indoors around people, this was the safer choice
  • Built in ROS console, map viewer, behavior tree editor, and network manager
    • This can also be turned off in favor of RViz or Foxglove, but I wanted a standalone method of data viewing and testing.

SLAM is provided by the SLAM toolbox, with two Slamtec C1 lidars covering each other's scan occlusions, and depth imaging by the Arducam ToF camera in the front.

I also created a rudimentary behaviour tree editor. Since the device can speak to so many sensors at the same time, I’m viewing it as a tool to quickly model and test sensor interactions for spatial installations.

Iterative Prototyping Method

To test different hardware orientations as fast as possible, I built the robot around a 300 x 300 optical breadboard I had left over from a previous job. The threaded holes were milled at +/- .003” on their centers, and when combined with two reference edges I was confident my component placement would mirror CAD well enough for these purposes.

Using Onshape, I developed a custom Featurescript that allows richer 6 DoF component positioning than their stock tool, and used it to create a mate connector for every component I can quickly reposition.

Next Steps

Reducing part count and wire bundles — once I'm happy with component placement, I'll design singular bodies to house multiple components and move to a permanent board. Then: new sensors, and dreaming up installations for this little robot to explore.
